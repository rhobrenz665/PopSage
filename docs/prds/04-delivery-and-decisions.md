# PopSage v1 — delivery, measurement, and decisions

Status: Approved product baseline companion to [the product brief](README.md) · 3 November 2026

## Current training constraints

This is a personal software engineering training project coordinated and tested by the project owner using fictional businesses, sample websites, and approved test documents. No business pilot, paying customer, production readiness certification, or measured service capacity is assumed. Local implementation began on 3 November 2026 with the Next.js application scaffold. Cloud provisioning, paid services, billing activation, and real business/customer data still require separate explicit approval.

Initial deployment targets US$0/month. Research genuinely recurring free allowances separately from one-time trials, promotional credits, and paid usage. US$50/month is an optional future pilot scenario only. Do not purchase or activate paid services without explicit user approval, and never silently fall back to a paid provider on quota exhaustion.

No country-specific training hosting requirement applies. Prefer US East where supported to reduce cross-service latency, while recording each service's actual hosting region and data destinations, including auth, source files, vectors, prompts, jobs, logs, and backups. This preference is not a residency guarantee. Reassess privacy, data residency, compliance, and provider data settings before introducing real business/customer data.

## Architecture intent

The training providers are selected at the architecture level: Vercel Hobby hosts Next.js, Neon Free provides Postgres/pgvector, managed owner/team authentication, and private object storage, Trigger.dev Free provides durable jobs, PartyServer/PartySocket on Cloudflare provides realtime, and Cloudflare Workers AI is the initial AI provider with future OpenAI adapters. US East is the preferred training region where supported. Exact models, invitation details, visitor-session design, and remaining operational settings remain open. No provider approval authorizes implementation, account creation, deployment, or paid activation.

| Component | Requested responsibility | Boundary to preserve |
|---|---|---|
| Iframe widget | Visitor messages and live replies; visitor token | Public workspace installation ID is not a secret or authorization credential. |
| Dashboard | Owner and teammate setup, knowledge, and conversations | Authenticated workspace membership controls all actions. |
| Next.js server | API, authorization, orchestration, query embedding, publication | Server decides workspace scope and persists authoritative state. |
| Neon Managed Better Auth | Owner/team login and session verification | PopSage independently checks workspace membership and roles. Visitor tokens remain a separate scoped access path. |
| AI capability adapters | Independently configured classification and generation; Cloudflare initially, OpenAI future | Separate provider-independent contracts; no mandatory commercial gateway. Credentials remain server-side; application scope, limits, and grounding checks surround calls. |
| Neon Postgres + pgvector | App data, chunks, vectors, workspace-scoped search | Persisted records are authoritative; tenant isolation is enforced beyond UI filtering. |
| Neon Object Storage | Private originals and presigned uploads | Verify completed objects; enforce access and deletion boundaries. Object paths do not grant authorization. |
| Trigger.dev Free | Parse, chunk, embed, migrate indexes, and clean up knowledge | Durable jobs, bounded retries/concurrency, idempotency, and visible terminal status. Postgres owns authoritative job outcomes. |
| Vercel Hobby | Next.js application, widget assets, and HTTP APIs | Personal noncommercial training only; quota exhaustion must not activate a paid plan. |
| Embedding adapters | Cloudflare Workers AI initially; OpenAI future | Select independently from generation/classification; versioned profiles and explicit re-embedding/index migration prevent incompatible retrieval. |
| PartyServer + PartySocket on Cloudflare | Authorized realtime delivery to widget and dashboard | Postgres is authoritative; reconnect recovers persisted state, access changes revoke live authorization, and quota exhaustion does not trigger paid service. See ADR 0006. |

Use a transactional Postgres outbox to close the gap between database commit and PartyServer live delivery. Commit durable state and event atomically; dispatch at least once with idempotent consumers and cursor-based reconciliation. A persisted message survives publish failure, while a rolled-back database change produces no durable event. Conversation rooms carry authorized transcript events; workspace inbox rooms carry summaries/state only. See ADR 0010.

Minimum domain concepts: workspace, membership/role, visitor session, conversation/state/assignee, message/sender/status, document/processing state, source chunk, ingestion job, outbox event/cursor, and AI decision/usage record. These define shared language, not a mandated database schema. Every tenant-owned record has an enforceable workspace relationship and is protected by application authorization plus Postgres RLS where applicable. See ADR 0011.

## Provider configuration and growth

- Use environment-based provider selection, endpoints, credentials, model IDs, regions, and operational limits. Keep secrets server-side and isolate training from any future production environment. Validate configuration explicitly; a missing free-tier key must not select a paid fallback.
- Keep narrow boundaries around auth/session verification, object storage, realtime publication, background jobs, classification, generation, and embeddings. Keep workspace authorization, durable state transitions, and conversation policy in application-owned logic, not duplicated in provider-specific handlers.
- Use only the boundaries needed by the MVP; do not build a universal plugin framework, duplicate infrastructure, or operate duplicate services without need. AI is an explicit exception to single-adapter scope: design both Cloudflare and OpenAI adapters, with independent capability configuration, but activate only approved providers. Provider replacement should change adapters/configuration rather than business rules.
- Configuration alone cannot make migrations free: embedding changes require compatible query/document configurations and reindexing; auth, storage, and realtime replacements may require explicit data/session migration. Document those upgrade paths.
- Preserve bounded concurrency, idempotency, recovery, and tenant isolation at free-tier scale. Record quota ceilings and graceful exhaustion behavior. Later paid tiers or provider replacements should increase capacity without redesigning the domain model.

## Shared quality requirements

- Unauthorized cross-workspace or cross-visitor access must fail across APIs, live channels, storage, retrieval, and jobs. Verify access revocation on established sessions.
- Render visitor, teammate, and document-derived content safely. Do not execute uploaded content or allow messages to inject host-page scripts. Keep credentials and private source URLs out of public responses and logs.
- Apply the approved inactivity and retention lifecycle in training; finalize physical cleanup and backup deadlines before deployment. Reassess data policies before accepting real customer data. Do not imply that deleting a source also deletes historical conversation text or provider-held data.
- Instrument failures and allow operators to identify stuck jobs, stale waiting conversations, and elevated provider errors without transcript access by default. Troubleshooting requires explicit workspace-owner authorization, a recorded reason, narrow scope, bounded duration, revocation, and an audit trail; see PRD 01 and ADR 0004.
- Keep the human chat path usable during AI failures. Recovery from transport failure must preserve accepted messages and ownership.
- Validate keyboard/screen-reader basics and responsive widget usability on the agreed browser matrix. Native mobile apps remain excluded.

## Success measures

The founder approved these targets on 3 November 2026. They are acceptance goals, not measured baselines or proven capacity. Engineering must validate fixtures and load. The initial spend target is US$0; performance/load goals remain future capacity goals until demonstrated within permitted quotas. Run training tests at an explicit quota-safe scale and report that scale rather than claiming the original load passed. Do not activate paid resources to satisfy a test.

| Measure | Definition and approved target | Evaluation window |
|---|---|---|
| Working-product milestone | One sample external site completes upload → supported answer → human request → human reply → closure with preserved history. | Training milestone. |
| Grounded answer quality | ≥95% of emitted answers to labeled support cases are correct and every material claim is supported by active workspace sources. Separately require answers on ≥80% of cases labeled answerable, so refusing everything cannot pass. | Initial ≥100 labeled cases, including ≥30 answerable support cases; report raw counts and per-category results. |
| Routing quality | ≥95% of clearly off-topic cases declined; ≥95% of on-topic unsupported cases handed off. All explicit human-request test cases hand off. Relevant unsupported questions must not be counted as off-topic successes. | Same evaluation set, with ≥20 off-topic and ≥20 unsupported cases; remaining cases cover context, ambiguity, conflict, and adversarial inputs. |
| Handoff continuity | 100% of scripted handoffs retain transcript and reason; zero committed AI replies after handoff/takeover. | Functional and race-condition suite during training; repeat before any real pilot. |
| Live message latency | p95 ≤1 second from server acceptance to rendering for a connected recipient. | Future capacity goal: 50 simultaneous widget sessions, five agents, aggregate five visitor messages/second; measure separately from AI answer latency. |
| AI answer latency | p95 ≤10 seconds from accepted eligible message to first visible validated answer content. Timeouts/failures reported separately, not discarded. | Measure at documented free-tier training load first. Original capacity goals require separate quota/cost validation before a future pilot. |
| Knowledge readiness | ≥95% of supported readable files up to 5 MB Ready within two minutes of verified upload. | Representative format fixtures under documented training load; larger files reported separately. |
| Visitor task completion | Approved ≥80% of ≥20 observed support sessions reach an evaluator-confirmed correct answer or a human response addressing the request. Queuing alone is not completion. | Scripted/observed training sessions initially; real-business validation remains a separate future gate. Report sample size and failure reasons. |

Track AI-only resolution as a diagnostic, not a launch gate: confirmed resolved conversations with no human reply divided by eligible support conversations. Silence, a closed widget, or an abandoned waiting queue is not evidence of resolution. Use training observation/manual review rather than adding a customer analytics feature to v1.

Track handoff rate, queue wait to first human reply, false refusals, ingestion failures, model token consumption, and AI cost per handled support conversation. Cost includes classification, query embeddings, generation, and failed/retried calls; ingestion costs are reported separately. Initial budget is US$0, with service-level quota controls to be selected; no cost estimate is fabricated here.

Minimal events: workspace_created, widget_connected, message_accepted, message_delivered, document_uploaded, ingestion_ready/failed, classification_completed, retrieval_completed, ai_answer_committed/discarded, handoff_requested, conversation_claimed, human_message_sent, conversation_closed, conversation_abandoned, conversation_expired, troubleshooting_access_granted/used/revoked/expired. Include scoped IDs, timestamps, outcome/reason, and configuration versions as applicable. Define delivery events as client-render acknowledgments for latency measurement; server publication alone is not recipient display.

## Delivery sequence and release gates

| Stage | Demonstrable result | Exit condition |
|---|---|---|
| 0. Plan and research (current) | Project owner reviews approved scope, free-tier provider proposals, lifecycle, and fictional evaluation cases. | Resolve open provider and operational decisions; confirm shared understanding and explicit implementation authorization before runnable work. |
| 1. Human chat slice | Sample website widget and dashboard exchange persisted messages. | Isolation, retry/reconnect, claim/reassign, closure, and access-revocation scenarios pass. |
| 2. Knowledge slice | Owner uploads supported files; Ready knowledge is searchable and removable. | Format/error fixtures, atomic publication, tenant isolation, retry, and removal races pass. |
| 3. AI and handoff slice | Supported answers, refusals, and human takeover operate in the same transcript. | Labeled quality/routing gates and late-output suppression pass; outage fallback works. |
| 4. Training evaluation | Project owner tests fictional businesses, approved documents, and sample websites. | No unresolved isolation/data-loss defects; free-tier exhaustion and retention/access scenarios pass; measured quality and capacity reported honestly. |
| 5. Optional future business pilot | Revisit the earlier three-business, two-week proposal after the training slice. No business participation is assumed. | Actual business representatives validate answers; recruit and arrange staffing; reassess privacy/residency/compliance; approve scope, cost, and real-data introduction explicitly. |

No launch date is committed. The project owner is coordinator and tester; implementation capacity and schedule remain open. After implementation is authorized, demonstrate each training slice before expanding scope. Estimate any real pilot only after the sample-site slice works; the earlier two-week pilot cadence is conditional, not a current customer commitment.

When implementation/testing is authorized, seed two independent workspaces and verify cross-tenant denial everywhere. Exercise reconnects, duplicate requests, worker crashes, document removal during generation, simultaneous claims, takeover during generation, provider outages, and AI budget exhaustion. There must be no observed tenant leakage, accepted-message loss, or post-handoff AI reply in these tests; include inactivity closure/new-message races and scoped troubleshooting-access denial. Passing does not establish a universal absence of defects.

Rollout starts with controlled access and workspace-level AI enablement. If grounding quality regresses or AI failures spike, disable AI and preserve human chat. Suspected isolation failures require stopping affected access and investigating, not merely toggling the model. The project owner coordinates training; assign real operational coverage before a business pilot.

## Scope review

Requirements preserve the requested A/B/C flows and explicitly exclude email/ticketing, help center, tours, native apps, and monetization. Additional details focus on making those flows reliable: clear document readiness, contextual classification, evidence-based abstention, single conversation ownership, and durable messaging. Screen layouts, endpoint names, schema design, chunk sizes, and specific models remain engineering/design decisions.
